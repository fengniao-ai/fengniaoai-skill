# 蜂鸟AI 电商商品套图

编排原子能力，不复制其 HTTP 实现。进入套图策划后读取 `../../references/ecommerce-visual-guidelines.md`，只提取当前平台、市场、品类和图片用途需要的规则。

## 对话顺序

1. 首先获取商品素材。用户提供 1688、淘宝/天猫或 Amazon 商品链接时，先用 `fengniao-product-insight` 采集并下载资料；只有通过其采集成功门槛后才展示标题、属性和图片清单。采集失败、`product.json` 无效或没有成功落盘的主图时立即结束本次 URL 套图流程，不自动重试，不调用浏览器、WebFetch 或其他抓取方式兜底，不继续卖点建议、套图规划、点数确认和付费生成，也不建议按文字描述生成原商品套图。用户随后提供新的可信链接或主动上传真实商品素材时，才作为新的链接或本地素材流程重新开始。用户直接提供本地商品图片或公网 HTTPS 图片时直接采用。后续场景图和卖点图使用参考图生图；看不清的颜色、文字、材质和配件不要猜测。
   用户明确要求分析时，说明主图数量和每张 0.5 点后分析全部去重主图；用户只要求制作套图时，推荐全主图分析并给出预计点数，让用户选择“分析后规划”或“直接用现有素材规划”，不能静默增加识图扣点。超过 10 张时让用户确认全部或选择范围。SKU 图只在变体差异影响套图时追加，详情图只在需要核对卖点、包装或版式时追加。采集信息与多图识别结果冲突时让用户确认。
   用户选择“分析后规划”时，必须读取完整 `product.json` 并结合逐图结果生成 `analysis/product-analysis.md`。进入卖点建议和套图规划前完整读取该文档；存在会影响商品身份、SKU、销售单位、尺寸、重量、材质、品牌或可见文案的关键冲突时先让用户确认。未生成综合分析或关键冲突未确认时，不建立最终商品一致性锁，不启动付费套图生成。用户选择“直接用现有素材规划”时明确标注未做综合识图分析，并只使用页面采集信息和可见参考图，不把不确定字段当作事实。
2. 下一轮只给出核心卖点建议，并询问用户采用、修改还是提供自己的卖点；可同时询问是否有明确风格偏好，不混入平台配置。
3. 用户确认卖点后，再补齐平台、目标市场、产物语言、比例和图片数量。用户已主动提供的信息直接采用；缺少地域信息时使用“通用电商”，不默认套用美国市场审美。
   只有成图包含可见文字时才确定产物语言，并按“用户明确指定 > 明确站点或目标市场 > 平台默认 > 询问用户”解析。Amazon 未指定站点时默认英语，淘宝、天猫、京东、拼多多和抖音默认简体中文，OZON 默认俄语；多市场平台没有目标市场时询问。平台默认不能覆盖用户要求，Agent 的中文过程说明不能写进成图。
   用户提供的精确文案必须逐字保留；文案与目标语言冲突时先询问是否翻译，不能静默翻译或改写。
4. 先按用户表达确定资产范围，不能只凭平台名称扩大任务：
   - “Amazon 主图”只规划主图；“Amazon Listing/主副图”只规划 Listing；“Amazon A+”只规划 A+；“Amazon 全套、主副图加 A+”才同时规划两者。“Amazon 套图”默认先规划主副图，并在同一次确认中询问是否增加 A+，不能静默增加 A+ 和计费操作。
   - “淘宝/天猫主图或套图”默认规划 5 张用途不同、设计丰富的商品主图，不默认加入白底图；只有用户明确要求白底图时才加入。“淘宝/天猫详情页”进入独立的模块化详情流程，不与 5 张主图混为一组。
   - 用户已经明确图片用途、数量或范围时直接服从；“只做”“不要”“不需要”等排除表达优先于平台默认。
5. 根据数量规划不同图片用途。默认不展示风格选择，由 Agent 自动定调；只有用户明确想看不同风格时，才展示 3–4 套简短 Markdown 风格卡片。
   规划前先列出素材实际支持的角度。只有真实参考图清楚展示正面、侧面、背面、开口、接口或包装结构时，才能规划对应视图；缺少侧面或背面证据时，自动改成已有素材支持的正面、细节或佩戴图，不能让模型补造结构。
6. 用表格列出每张图的任务 ID、资产类型/模块、目标颜色/SKU、用途、本张展示约束、有序参考图、参考理由、生成比例、最终交付尺寸、交付处理、语言和计费操作。参考图使用“参考图 N（稳定文件 ID）”表示；先完成分配再写 Prompt，不输出内部 JSON。
7. 淘宝/天猫详情页始终把每个模块作为一张独立图片提交生成并分别交付，不询问或承诺拼接成长图。移动详情模块默认优先 `3:4`，内容较长可用 `2:3`，方形信息块可用 `1:1`。用户明确要求“长图、整页、一张上传”时，直接说明当前 Skill 只交付独立模块图，并询问是否按独立模块继续；不能通过再次生图模拟整页长图。
8. 使用 `node ../../scripts/fengniaoai.mjs account balance --input-json '{}'` 查询剩余点数。
9. 这是多操作工作流，执行前必须确认图片数量和计费操作；A+、详情模块和不同尺寸分别计入清单，不能因一句“套图”静默增加。

如果用户一次性给齐素材、卖点和上架配置，直接整理并确认，不强迫用户重复多轮问答。用户说“你来定”“好看就行”时自动选择风格，不增加一次选择。

## Prompt 组装

1. 按图片用途为每张图分别组装 Markdown Prompt，不要求风格策划或生图接口返回 JSON。
2. 先从 `product-analysis.md` 的“用户确认后可用于规划的商品事实”建立不含展示数量的商品身份锁；多色或多 SKU 产品为每个变体建立独立身份锁。同一变体的 Prompt 逐字复用对应身份锁，整套 Prompt 复用完全相同的“套图统一视觉基线”；把单件、整卷、使用状态或组合数量放进各自的“本张展示约束”。不能把完整 `product.json`、字段异常、来源冲突或待确认信息直接写进 Prompt。
3. 每张只加入目标平台和目标市场对应的规则，不把完整平台、市场知识表塞进 Prompt。
4. 按参考表区分“接口生成比例”和“平台最终交付尺寸”；平台明确排除的比例不能被用户通用偏好覆盖，其他不支持比例也不能静默替换。OZON 商品图必须显式传递 `aspect_ratio=3:4`，不能依赖 `image transform` 的 `original` 默认值。用户坚持 `1:1` 时，说明它不能作为 OZON 标准商品图交付，并询问是否改为通用电商图片；未确认改类前不执行付费生成。需要固定像素时先按支持比例生成内容图，再用确定性工具裁切或缩放；多比例版本分别计费。
5. 具体场景、构图、商品占比和唯一卖点随图片用途变化；字体和图标规则只用于确实需要文字的信息图。
6. 将完成后的 Markdown 直接作为 `image transform` 的 `prompt`，参考商品图通过 `image` 或 `reference_image_urls` 单独传递。
7. 未使用的模板章节直接删除，不把占位符传给接口，也不向用户展示内部 Prompt。

## 执行顺序

1. 白底主图使用 `fengniao-image-generate` 的 `image transform`；只有用户明确说“抠图”“去背景”“移除背景”或“抠出主体”时，才使用 `fengniao-image-tools` 的抠图输出。
2. 使用 `fengniao-image-generate` 的 `image transform` 逐张生成白底主图、场景图和卖点图；每张使用新的 `request_id`。
3. 多平台比例使用生图扩图能力，不调用旧扩图接口。
4. 仅在用户要求本地化版本时使用 `fengniao-image-translate`。
5. 单色或单 SKU 产品选择一张商品完整、无遮挡、少道具和少营销文字的身份主图，固定为该变体每个任务的参考图 1；多色或多 SKU 产品按变体分组，每组使用自己的身份主图，不能跨颜色复用。每张任务只追加零至两张与本张角度、结构、材质、尺寸或场景直接相关的证据图。多变体同框图为每个变体传一张干净身份图并设置 `reference_mode=variants`，不得把第一个颜色当作其他颜色的主基准。`reference_roles` 必须使用“稳定文件 ID｜颜色/SKU｜职责”，Prompt 按最终数组编号引用“参考图 N（文件 ID）”。已有经用户认可的主视觉只能作为最后一张风格参考，不能替代原商品图。
6. 生成任务成功只依据持久化批次 manifest 的终态和产物落盘，不能等待视觉读取工具才补入下一张或判定批次完成。按商品一致性锁逐张检查属于独立的视觉验收阶段；明显漂移时标记问题，不自动付费重试，先获得用户确认。检查结论使用“AI 初检通过”“需修正”“等待商家确认”，不能把生成式检查称为已经合规或可直接上架。
7. 完成后先给出总数、成功数、失败数、消耗点数和结果目录；正常规模套图再给出全部结果路径并逐张展示图片、用途、比例、语言和检查状态，大批量只展示汇总与最近结果，不在对话铺开数百条路径。展示文件不等于同时读取多张图片做视觉分析，不能只展示一张代表图后让用户自行翻目录。远程 URL 与 request ID 仅在用户要求或排查问题时展示。批量文件直接保存为 `<batch_dir>/<id>.<实际格式>`；用户要求重做某张时，传对应 `task_ids` 先报价并确认，结果保存为 `<id>-v2`、`<id>-v3`，不得覆盖旧图。任务 ID 使用用途型名称且不能重复。
8. 共享相同身份主图和证据图的套图从 2 张起必须使用 `fengniao-image-generate` 的持久化批量 action，不能临时编写 Shell 脚本、循环调用或并行启动多个单图命令替代。所有任务参考图完全相同时放进 `shared`；某张需要不同证据图时，在该 task 中传包含身份主图的完整有序数组和等长职责，不能只传增量。新对话先用 `batch-list` 找回最近批次。批量执行器使用最多 10 个工作槽的滑动队列：任一任务结束后按原顺序立即补入下一张，始终不超过 10 个在途请求。服务端 20 QPS 是每秒提交上限，不是在途任务上限；多个 Agent 共用同一账号时仍以服务端合计限流为准。遇到 `429/30001` 时保留原 `request_id` 并按 `../../references/actions.md` 退避；连续限流时暂停队列，不无限循环。任务清单持续记录用途、Prompt、参考图顺序、比例和 request ID，重做时只提交指定图片。
9. 视觉验收使用独立小队列：当前 Agent 的图片工具明确支持单次超时、取消和终态回收时，最多同时读取 2 张并为每张设置不超过 60 秒的工具超时；缺少其中任一能力时不自动调用视觉读取，直接展示结果并标记“等待商家确认”。用户在交付后明确要求 AI 检查时才一次读取 1 张，仍不得并行。读取失败、超时或工具不可用不能阻塞已启动的生成队列、剩余图片、批次恢复或成功结果。平台支持后台 worker 时，可以在生成队列继续运行的同时检查已经完成的图片；不支持时先完成生成和路径交付，再开始检查。
10. 详情页各模块作为独立批量任务生成、验收和交付；当前 Skill 不提供模块拼接，不生成或承诺整页长图。

不承诺生成图片能精确保留商品文字或让跨图商品像素级一致；需要文字准确性时使用确定性的 OCR/翻译工具。成功时优先展示自动下载的 `local_path`。
